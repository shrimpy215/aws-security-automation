The solution

What you're actually building

A finding arrives. Within seconds the system has decided whether it matters, whether it has seen it before, whether anyone needs to be told, and whether the affected resource should be taken off the network — and has written down each of those decisions.

The hard part is not the wiring. It is deciding what not to do: which findings to ignore, which repeats to swallow, and which resources are never safe to touch automatically. Most of the code below exists to enforce those refusals.

Structure

Three stacks, split by lifetime

The usual instinct is to group infrastructure by service. This is grouped by how long each piece should live — which turned out to be the decision that made the project cheap to run and fast to iterate on.

guardrails/
Permanent
Account budget with forecast alerting. Never destroyed. A cost control that can be torn down alongside the thing it guards is not a control.
detection/
Project duration
GuardDuty, Security Hub, Config, the KMS key, the SNS topic. Slow to enable — standards take hours, an email subscription needs a human to click a link.
workload/
Per session
Lambda, DynamoDB, EventBridge, IAM. Destroyed at the end of every working session, back in about thirty seconds.

The workload stack reads nothing from the detection stack's state file — it finds the key and topic by name through data sources. The two are genuinely independent, which is why one can be destroyed nightly while the other stays up.

Why it matters

A KMS key cannot be deleted on demand; destroy only schedules deletion, minimum seven days, and it bills the whole time. An SNS email subscription silently discards messages until someone clicks a confirmation link. Both would have been re-created every session. Neither belongs in a stack you tear down twice a day.

Triage

Four outcomes, all of them recorded

Every finding that enters the system leaves a record of what was decided about it — including the ones deliberately ignored. That last part was a late change, and the right one: "we saw this and chose not to escalate" is exactly the decision an investigator or an auditor would want proof of.

OutcomeWhenAlert sentAudit row
BELOW_THRESHOLD Normalized severity under 40 No Yes
SUPPRESSED_DUPLICATE Fingerprint already claimed inside the 24-hour window No Yes
TRIAGED New finding at MEDIUM or above Yes Yes
CONTAINED HIGH or above, on a tagged resource, all guardrails cleared Yes Yes, with rollback data

Deduplication is on meaning, not identity

The fingerprint is a hash of finding type plus affected resource — not the finding ID. Two separate findings describing the same problem on the same instance collapse into one alert; the finding ID would have kept them apart.

The claim is a DynamoDB conditional write, not a read followed by a write. Two Lambda containers processing the same finding simultaneously would both see "not present" and both send an alert. The conditional write makes the check and the write one atomic operation, so exactly one wins.

Two tables, not one

Suppression state is supposed to expire — that is the mechanism, and TTL reopens the window so activity that resumes is treated as new rather than silently swallowed. An audit record must never expire. Two requirements in direct opposition, so they get two tables: one with TTL and no point-in-time recovery, one with recovery and no TTL.

Containment

Four guardrails, and one of them enforced twice

The remediation function holds ec2:ModifyInstanceAttribute and iam:UpdateAccessKey. Everything below exists to make that safe.

1 · protected allow-list

Named resources are never touched, whatever the finding says. Checked first, so a protected resource is refused even when every other condition would permit action.

2 · severity threshold

Normalized 70 and above only. Terraform refuses to deploy a threshold below MEDIUM — a validation rule guarding the guardrail.

3 · required tag

The resource must carry SecurityAutomation=enabled. Enforced in Python, and again by an IAM resource-tag condition that AWS evaluates independently.

4 · dry run

Defaults to on. A missing or misspelled environment variable results in no action rather than unintended action.

Credential revocation follows the same principle: keys are set to Inactive, never deleted. Reversible if the finding turns out to be a false positive, and still available for working out what the key was used for.

Measurement

Response time, reported honestly

Measured from live GuardDuty findings, whose timestamps AWS sets. Synthetic test fixtures are excluded from the calculation — their createdAt values are hardcoded, so any interval measured from them is fiction rather than latency.

Median detection-to-decision was 3.0 minutes, range 1.2 to 4.8. Nearly all of that is AWS-side publishing delay. Reporting one blended figure would hide the fact that this pipeline's own contribution is under a third of a second — and that any real improvement would have to come from the detection source, not from this code.

What this is not

MTTD in the NIST SP 800-61 sense is the interval between compromise and detection. That is not measurable here: sample findings describe events that never happened, so there is no compromise time to measure from. Calling this MTTD would be the easy claim and the wrong one.

Build sequence

Seven stages

  1. Repository and cost guardrail complete
    Directory structure, gitignore, and an account budget with alerts at 50% actual, 100% actual, and 100% forecast — deployed before anything billable existed, in its own state file so no teardown can remove it.
  2. Detection foundation complete
    GuardDuty with optional paid data sources explicitly disabled, Security Hub with CIS v3.0.0 and AWS Foundational Security Best Practices, and an AWS Config recorder so the benchmark controls have configuration items to evaluate.
  3. Persistence and alerting complete
    Customer-managed KMS key with rotation, an encrypted SNS topic with a confirmed subscription, and the two DynamoDB tables with their deliberately opposed retention policies.
  4. Triage function and event routing complete
    Python handler normalizing two incompatible finding formats into one internal shape, severity filtering, race-safe deduplication, audit writes, SNS alerting. EventBridge rules with scoped invoke permissions and a dead letter queue.
  5. Guardrailed containment complete
    Second function, second IAM role, four guardrails, tag-scoped IAM conditions, reversible actions with rollback data recorded. Demonstrated live against a throwaway target and restored afterwards.
  6. Verification and measurement complete
    An 18-assertion harness that exits non-zero, and a Python tool computing latency from the audit trail. The harness immediately found a live defect: an indentation error had made the MEDIUM path unreachable, and manual testing had missed it.
  7. Playbook, README, and CI complete
    Incident response playbook mapped to NIST SP 800-61, twenty-two design decisions, a troubleshooting log, and CI running format, validate, Checkov and Python lint on every push. Checkov's one fair finding — missing X-Ray tracing — was fixed rather than skipped; the rest are documented exceptions that argue their case.
  8. Teardown and publication complete
    Both stacks destroyed, and the teardown verified by querying AWS directly rather than trusting the destroy output. Only the permanent budget guardrail and a pending-deletion KMS key remain, both by design. Pushed with CI green.

Lambda, DynamoDB on-demand, SNS and EventBridge are all effectively free at this volume. AWS Config is the exception — it has no free tier and bills per configuration item — which is why it sits behind a variable that can turn it off, and why the tradeoff is documented rather than absorbed silently.

The workload stack is destroyed at the end of every session and rebuilt in about thirty seconds, so nothing accumulates between working days.

Positioning

What this proves

Projects 1 and 2 demonstrate building secure infrastructure. This one demonstrates operating it: what happens after a control fires, who finds out, how fast, and what the system is permitted to do on its own.

Each project in the portfolio is a standalone deployment — this one shares no resources with the earlier two, which were destroyed before it began. What carries forward is the conventions: stacks split by lifetime, a decisions log written as the work happens, verification committed rather than described, and CI exceptions that argue their case instead of suppressing findings.

For a security operations screen, the deduplication and audit design are the substance — alert fatigue is the reason most detection programmes quietly stop working, and TTL-scoped suppression with a permanent audit trail is a real answer to it. For a cloud security architecture screen, the interesting part is the IAM: a function holding genuinely destructive permissions, constrained by a resource-tag condition that AWS evaluates independently of the code.

The paragraph that matters

"The tag guardrail is enforced twice — once in Python, once by an IAM condition — because code can have bugs and the IAM policy is the backstop that survives them."

Being able to say that, and then explain the three-line policy condition that makes it true, is the difference between having built automated remediation and being trusted to point it at production.
